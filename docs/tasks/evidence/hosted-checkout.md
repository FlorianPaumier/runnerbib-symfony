# Hosted checkout submission checkpoint — 2026-10-11

PAY-02 submission is implemented through `SubmitHostedCheckout::submit(operationId, checkoutId, now, worker)`, its scope-bound PostgreSQL journal adapter and the Stripe SDK adapter. This checkpoint does not establish paid purchases, signed webhook processing or financial recovery.

Before an external mutation, an owning database transaction verifies the original operation/checkout/provider scope, initial deadline and original attempt. It commits one stable idempotency key, payment attempt, lease and fencing generation. The provider runs after this transaction commits. Lost responses become unknown; retries inside the original application window reuse the exact attempt/key. A known original Session is retrieved on redelivery, without another creation. An active lease excludes another worker; late workers cannot overwrite a newer fenced result. Passing the initial 900-second deadline does not release protection or authorize blind unknown-outcome replay.

`HostedCheckoutMessageHandler` accepts only the versioned checkout payment event, a checkout aggregate and a strict operation-ID-only payload. The persisted operation must belong to that aggregate. Invalid, unrelated or unsupported messages cannot call the provider. The handler uses the installed PSR clock implementation and its normal composition-root event tag.

The Stripe adapter creates one hosted platform card payment for the exact committed EUR buyer total, with French locale, automatic tax disabled, original HTTPS callbacks, pinned API version and correlation metadata on both Session and PaymentIntent. The aggregate hosted line is named “Commande de dossards”; the immutable local checkout contains the complete itemized money and registration snapshots. Buyer private fields are not sent in the operation parameters. No short Stripe `expires_at` is supplied: the [Session API](https://docs.stripe.com/api/checkout/sessions/create) requires at least 30 minutes, while the application retains its separate initial 15-minute deadline. The separate original-session reconciliation slice below enforces that deadline through explicit expiration.

The SDK response must match the expected amount, currency and checkout identity. Redirects must use HTTPS on the Stripe Checkout host. Session retrieval checks the original identity and allows a null URL for a closed path; neither creation nor retrieval confirms payment or creates a purchase. Factory defaults are explicitly unconfigured and refuse before preparing a submission attempt. No real Stripe keys, accounts or provider requests were used for these tests.

## Original-session lifecycle reconciliation

`ReconcileCheckout::reconcile(checkoutId, now, worker)` claims the existing checkout lease and fencing generation, then inspects the original Session outside the transaction. The SDK retrieves its expanded original PaymentIntent using the committed API version, and validates money/currency/correlation on both objects. Missing, contradictory or uncertain facts retain all protected items. Paid or processing paths retain protection until backend payment validation and whole-purchase finalization.

At the initial 15-minute deadline, an open original Session gets a durable cancellation request before the provider call. The expiration uses stable `checkout-expire:{checkoutId}` identity and the committed API version. A subsequent authoritative read must establish an expired unpaid Session with no PaymentIntent or a confirmed canceled original PaymentIntent before release. The [Stripe expiration API](https://docs.stripe.com/api/checkout/sessions/expire) closes open Sessions; errors or lost responses do not establish closure. An expired Session whose intent remains actionable, processing or unknown stays protected pending the next cancellation/recovery slice.

Confirmed safe closure atomically releases all checkout items and buyer/race guards, updates payment-attempt reconciliation state and preserves snapshots and the original financial operation. A never-submitted checkout can release at its deadline without a provider call. Before that deadline it remains pending and allows first submission; an unknown original submission can replay only the same operation/attempt/idempotency key within its original deadline.
